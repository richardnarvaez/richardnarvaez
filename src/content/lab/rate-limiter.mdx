## The problem

Users upload PDFs. **Every page is one call to an AI provider** that extracts and structures the text. A book is a hundred pages, so one upload is a hundred calls.

Me alone, uploading three or four books one after another: fine. All pages in parallel: still fine. Then we opened it to everyone, a huge queue formed, and the provider said no.

The provider in the lab is a stand-in with the limits real ones have: 1,500 requests and 300,000 tokens per minute, 200 calls in flight at most, three dollars per million tokens. A page is about 800 tokens and takes about two seconds. Nothing leaves your machine and nothing costs money.

<Callout>
  Every case below has a **Run this case** button in the lab, which needs the lab running locally: `node provider/server.mjs` and `PROVIDER_URL=http://localhost:9090 node api/server.mjs` from the repo, then open http://localhost:8080. The numbers quoted are from those runs.
</Callout>

## Case 1 · One user, one page after another

The first version. A user uploads a book and we process it page by page: send one page, wait for the answer, send the next. **One call in flight per user.**

## Case 2 · All pages at once, and a few more users

Three minutes per book is too slow, so we fire the hundred calls together with `Promise.all`. One user: the book finishes in seconds. Then two, three users try at the same time. **Every user is now a burst of a hundred calls and eighty thousand tokens.**


The provider answers **503 Overloaded** for what does not fit in flight and **429 Too Many Requests** with a `retry-after` once the minute's tokens run out. Pages die, the user sees a broken book, and we still pay for every page that got through.

Measured: with three users it breaks in the first second. In fifteen seconds, 2,122 pages died at the provider, 3 of 25 books came out clean, and the bill was $0.90 for pages that mostly ended up in broken books. This is the day we opened it. [Run case 2](http://localhost:8080/?case=2)

## Case 3 · A rate limiter in front: the token bucket

First fix: never let more through than the provider accepts. Two buckets. **One per user**, small, five pages in a burst and two more per second, so one person cannot flood us. **One global**, pinned to the provider's requests per minute, so the sum of everyone never exceeds it. A page takes a token from both or is refused by us, instantly and for free, with our own 429.

  ]}
  caption="Two gates. Whatever does not fit is refused by us, before it costs anything."
/>

```ts
// token bucket, per key
tokens = Math.min(capacity, tokens + elapsed * refillPerSec)
if (tokens >= 1) { tokens -= 1; allow() }
else reject({ retryAfterMs: ((1 - tokens) / refillPerSec) * 1000 })
```

<Decision
  title="Token bucket over a fixed window"
  why="A bucket is two numbers per key and lets a user burst a few pages, which is how people actually behave. A fixed per-minute counter is simpler but lets twice the limit through at the minute boundary."
  tradeoff="Bursts up to the bucket size are allowed by design."
/>

<Decision
  title="The same bucket as a Lua script in Redis when there is more than one API instance"
  why="Read, refill and take must be one atomic step or two instances spend the same last token. Redis runs the script whole, and its own clock removes skew between servers."
  tradeoff="Logic lives in a Lua string. Keep it short and test it alone."
/>

The provider never sees the excess again: zero 429 on their side, zero wasted spend. But the failure only **moved**. Now it is our limiter answering 429 to real people, and a book of a hundred pages against a bucket of five still comes out broken. Good for protecting a paid API; not enough for this product. [Run case 3](http://localhost:8080/?case=3)

## Case 4 · A work queue: say yes, later

The users are not abusing anything; they are uploading books, which is the product. So instead of saying no, **hold the page and send it when the provider can take it**.

  notes={[{ x: 215, y: 175, text: "503 busy + position", hot: true, anchor: "middle" }]}
  caption="Two budgets because the provider has two limits. Fairness between users. A door that says no early when the wait would be absurd."
/>

```ts
// the dispatch loop
while (inFlight < concurrency && queue.size > 0) {
  const job = peek(nextUserInTurn())
  if (requestBudget < 1 || tokenBudget < job.tokens) break // wait for the next token
  requestBudget -= 1
  tokenBudget -= job.tokens
  dispatch(take(job))
}
// at the door: if (estimateWait(job) > maxWaitMs) reject busy(position)
```

<Decision
  title="Drain on two budgets, requests and tokens"
  why="Providers limit both, and a page is heavy in tokens. A queue that only counts requests would still hit the token ceiling."
  tradeoff="You need an estimate of tokens per job before sending it. For pages, the size of the text is a good enough proxy."
/>

<Decision
  title="Round-robin between users, not first come first served"
  why="One user uploading ten books must not delay everyone else by ten books. A lane per user and a turn each keeps the wait proportional to what you asked for."
  tradeoff="More bookkeeping than a single FIFO."
/>

<Decision
  title="Backpressure at the door"
  why="Accepting work you cannot finish in reasonable time is worse than a fast no. The queue estimates the wait on entry and refuses past a minute, with a position so the client can decide."
  tradeoff="Some users get busy on a spike even though the system is healthy. That is the point: it is honest."
/>

No provider errors, no wasted spend, and users get **waiting instead of failing**: a page might take twenty seconds, but the book arrives whole. The honest part shows up too: the queue protects the provider, it does not create capacity. When more books arrive than the provider can process per minute, the wait grows until the door starts saying busy. Past that point the answer is a bigger tier or more keys, and the numbers tell you exactly when. [Run case 4](http://localhost:8080/?case=4)

## Case 5 · What actually happened: the queue nobody designed

In production there was no queue and no limiter. So where did "a huge queue formed" come from? From the HTTP client. Every client library keeps a **connection pool**; ours allowed a couple of hundred connections to the provider. When thousands of pages arrived at once, they did not fail immediately: they **waited for a free connection**, in a queue we never wrote, with no fairness, no budget and no door. Latency climbed to minutes, users retried, the pool filled again, and when pages finally reached the provider they hit its limits anyway.

## Where it breaks

The lab has a ramp that adds users every three seconds, 1, 2, 3, 5, 8, 12, 20, 30, 50, 80…, and notes the first failure. With all pages at once and nothing in front, it broke with **3 users at second 7**, on tokens per minute. With the same crowd and the limiter, the provider stayed clean and our own 429 started at the same point. With the queue, nothing failed at the provider; the wait grew instead, and the door started saying busy when it would have passed a minute.

## What I would do in production

- Pages one after another per user was never the answer; parallel with a queue in front is.
- Size the queue's budgets from the provider's documented limits, not from guesses, and alert when the wait p95 crosses a threshold: that is the signal to buy a bigger tier.
- Show the position in the queue to the user. Waiting with a number is fine; waiting in the dark is what makes people retry and make it worse.
- Treat the HTTP client's pool as a queue you own: size it, measure it, and never let it be the only thing between you and a 503.
